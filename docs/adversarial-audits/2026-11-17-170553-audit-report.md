## Findings 详情

### [P1] AA-DATA-001 — 修掉 `DescribeEx` 按 `ToString` 生成 JSON 键导致的不同类型键互相覆盖

- **位置**：`packages/dsh-bridge/adapters/unity/probe/DSHBridgeProbe.cs.tpl` → `DescribeEx(...)` 的 `IDictionary` 分支
- **证据等级**：已验证（真机复现）
- **触发条件**：返回的字典/哈希表含**类型不同但字符串表示相同**的键，例如 `1`（int）与 `"1"`（string）；或自定义类型重写了 `ToString`。
- **错误行为**：
  ```
  输入：d[1] = "int-key"; d["1"] = "string-key"
  输出：{"1":"string-key"}
  ```
  `int-key` 被**静默丢弃**，既无告警也无 `resultTruncated` 标记。
- **影响**：ASE 侧数据模型里 nodeId / portId 常以混合类型出现（`int` 与序列化后的 `string`）。一旦命中，几何或属性清单会**少节点而不报错**，ASECLI 后续的布局与连线计算基于残缺数据，产出错误 shader —— 这正是「静默截断/丢数据」类最贵的失败。调用方无法从返回值察觉。
- **最小修复方向**：键编码为带类型前缀的字符串（如 `i:1` / `s:1`），或在检测到冲突时把该层降级为 `[{key,value}]` 数组并置 `resultTruncated=true` + `truncation.reason="key-collision"`；禁止静默覆盖。
- **关联优化任务**：AA-OPT-001

### [P1] AA-MEM-001 — 修掉 `_scriptingDiagnostics` 的跨调用无界累积

- **位置**：`DSHBridgeProbe.cs.tpl` → `static readonly List<string> _scriptingDiagnostics`；写入点 `CollectReferencesForMonoCompiler()`（`_scriptingDiagnostics.Add("mcs-refs:" + paths.Count)`）；清理点仅 `EnsureScripting()` 的 `Clear()`
- **证据等级**：已验证（真机读私有静态字段）
- **触发条件**：任何一次 `unity.code.execute`（Mono 编译器路径不经过 `EnsureScripting`，因此永不清理）。
- **错误行为**：
  ```
  调用 3 次 code.execute 后读取 _scriptingDiagnostics：
  count = 163
  ["mcs-refs:475","mcs-refs:475", ... ]
  ```
  每次调用追加一条，历史条目永久保留。
- **影响**：① 编辑器进程内无界内存增长（长时间运行的编辑器会持续累积）；② `code_execute_unavailable` 的 `detail` 由该列表拼接，条目越多越早触发 `Trim(..., 6000)`，**真正有用的缺失项会被历史噪音挤掉**，故障定位能力随使用时长下降。
- **最小修复方向**：在 `CodeExecute` 入口清空（与 `EnsureScripting` 一致），并给列表设上限（如 64 条，超出丢弃最旧）。
- **关联优化任务**：AA-OPT-002

### [P1] AA-OBS-001 — 让 `bridge-cli` 的安装与调用受同一套授权与审计约束

- **位置**：`scripts/bridge-cli.mjs` → `install` 分支（`unityAdapter.install(...)`）、`callCapability(...)`
- **证据等级**：已验证（代码审查 + 运行时对比）
- **触发条件**：任何本地进程执行
  `node scripts/bridge-cli.mjs call <project> unity.code.execute '{"code":...}'`
  或 `node scripts/bridge-cli.mjs install <project> --allow-dangerous unity.reflect.invoke,...`
- **错误行为**：
  1. **审计缺口**：调用前后 `~/.dsh/bridge/audit.log` 行数不变（实测 `73 → 73`），而经 DSH 插件的同一能力会写 `event:"call"`。CLI 只做了 `authorizeCapability` 的内存判断，**完全不写审计**。
  2. **授权绕过**：`install` 把命令行 `--allow-dangerous` 直接渲染进探针授权快照，不经过 `Bridge.install` 的配置来源，也不留安装审计。等于**一条命令即可给探针授予反射执行面**，无需改动 DSH 插件配置。
- **影响**：`AA-OBS-002`（审计覆盖所有调用）在 CLI 路径上失效；授权边界从「必须改插件配置并重启」降级为「命令行加个参数」。虽然本地攻击者本可直接改写 `Packages/com.dsh.bridge/Editor/*.cs`，但官方工具把门槛降到一行命令且**无任何痕迹**，事后无法区分「用户授权」与「本地进程擅自提权」。
- **最小修复方向**：`bridge-cli` 的 `install`/`call` 复用 `Bridge` 实例（或直接调用其 `audit.record`），把 `install` 的授权来源限定为「显式 `--allow-dangerous` + 控制台二次确认（非 TTY 时拒绝）」；审计记录 CLI 来源标记（`via:"cli"`）。
- **关联优化任务**：AA-OPT-003

### [P1] AA-LIMIT-001 — 为 `code.execute` 的不可中断执行提供可判定边界

- **位置**：`DSHBridgeProbe.cs.tpl` → `CodeExecuteViaMonoCompiler(...)`、`CodeExecute(...)`（均在 `EditorApplication.update` 回调内同步执行）
- **证据等级**：高置信推断（未动态验证：构造死循环会挂死用户编辑器，不作为审计手段）
- **触发条件**：脚本含无限循环、超长等待（`Thread.Sleep`）、或同步等待未完成 `Task`（后者已单独拒绝），或编译超大源文件。
- **错误行为**：主线程被占满且**无任何中断点**；探针 `Tick` 停止消费 inbox，后续所有请求（含 `unity.editor.status`）全部排队；DSH 侧 `timeoutMs` 仅放弃等待，探针侧仍在执行。编辑器 UI 无响应。
- **影响**：单次错误调用即可让编辑器不可用，且用户无法通过桥自救（必须强杀进程，丢失未保存场景）。这是本次改造引入的**新失败模式**（改造前最长阻塞是 `AssetDatabase.Refresh`，且已有 `editor_busy` 前置拒绝）。
- **最小修复方向**：① 执行前检查 `code` 长度与预估风险，超阈值需显式 `allowLongRunning:true`；② 执行后把 `elapsedMs` 与阈值比较并写入事件/审计，让「慢调用」可观测；③ 文档明确「不可中断」并在 ASECLI 侧把长任务拆小。Mono 无可靠 `Thread.Abort`，**不建议**尝试强杀线程。
- **关联优化任务**：AA-OPT-004

### [P2] AA-PERF-001 — 缓存 Mono 编译器引用集，避免每次调用重建

- **位置**：`DSHBridgeProbe.cs.tpl` → `CollectReferencesForMonoCompiler()`（调用点：`CodeExecute` 的 mcs 分支）
- **证据等级**：已验证（`mcs-refs:475` + `elapsedMs≈1082~1402ms`）
- **触发条件**：每次 `unity.code.execute`。
- **错误行为**：每次都执行 5 次 `Directory.GetFiles`（profile、Facades、Managed/UnityEngine、Managed/UnityEditor*、Library/ScriptAssemblies）+ 475 次 `AddPath`（`File.Exists` + 字典/`AssemblyName` 缓存查找）+ 遍历整个 `AppDomain`。CPU 与 IO 开销与「编译一小段脚本」同一量级，`elapsedMs` 中相当比例消耗在引用集构建而非编译。
- **影响**：ASECLI 的建图/几何流程单次就要 1–4s，重复调用被放大；编辑器主线程阻塞时间同比例增加（与 AA-LIMIT-001 叠加）。
- **最小修复方向**：以「工具链目录 + 程序集数量 + `Library/ScriptAssemblies` 目录 mtime」为失效键缓存整张引用集；域重载后自然重建（静态字段随域重置）。
- **关联优化任务**：AA-OPT-005

### [P2] AA-SEC-001 — 给 `references` 参数加路径白名单

- **位置**：`DSHBridgeProbe.cs.tpl` → `CollectReferencePaths(...)` 的 `explicitReferences` 分支（仅 `File.Exists` 检查）
- **证据等级**：已验证（真机传 `/etc/hosts` 被接受且编译成功）
- **触发条件**：`unity.code.execute` 传 `references:["/任意/本地/文件"]`。
- **错误行为**：接受工程外任意路径作为编译引用，探针不做 `ResolveProjectPath` 检查。实测 `{"code":"return 1;","references":["/etc/hosts"]}` 返回成功（`warningCount:1`），说明文件被读取并交给编译器。
- **影响**：与探针对 `asset.read`/`asset.create` 建立的 `path_escape` 策略（AA-OPT-002/003）不一致；构成「任意本地文件存在性探测 + 元数据读取」面。**增量风险有限**（`code.execute` 本就可执行任意代码直接读文件），但它是绕过 `_deniedTypes` 的现成通道（引用一个含黑名单类型的程序集后即可间接使用），且让「路径必须落在工程内」的安全叙事出现例外。
- **最小修复方向**：显式 `references` 只允许「引擎工具链目录」与「工程 `Library/ScriptAssemblies`」两个前缀（复用 `ResolveProjectPath`/`IsInsideProject` 的判定逻辑），其余报 `path_escape`。
- **关联优化任务**：AA-OPT-006

### [P2] AA-CONTRACT-001 — 明确 `batch` 在多项失败时的 `failedAt` 语义

- **位置**：`DSHBridgeProbe.cs.tpl` → `ApiBatch(...)`；`packages/dsh-bridge/docs/DETAIL.md` 的批量事务一节
- **证据等级**：已验证（真机）
- **触发条件**：`stopOnError:false` 且多个调用失败。
- **错误行为**：
  ```
  4 个调用，第 2、4 个抛异常
  failedAt = 3            ← 最后一个失败
  top-level error = "Exception: second"
  results[1].ok=false, results[3].ok=false
  ```
  `failedAt` 与顶层 `error` 都只反映**最后一次**失败，而文档与 V4 用例的语义暗示「失败发生的位置」。调用方若只读 `failedAt`/`error`，会以为「只有第 4 个失败、前 3 个成功」。
- **影响**：批量事务的失败诊断误导，尤其在 `stopOnError:false`（继续执行）场景下会掩盖中间失败，可能导致调用方漏做补偿。
- **最小修复方向**：明确并实现为「`failedAt` = 首个失败索引」，新增 `failures:[{index, code, message}]` 承载全部失败；文档同步。
- **关联优化任务**：AA-OPT-007

### [P2] AA-CLEAN-001 — 给验收脚本的 staging 文件加 `finally` 清理

- **位置**：`scripts/verify-bridge-capabilities.mjs` → V4 段（`Assets/__dsh_v4_staging.txt`）
- **证据等级**：已验证（代码审查）
- **触发条件**：V4 的 `api.batch` 调用本身失败（例如 `code.execute` 不可用、编辑器正在编译），此时 `onError` 里的 `File.Delete` 同样编译失败。
- **错误行为**：`catch` 分支只记录 FAIL，**没有删除 staging 文件**，`Assets/__dsh_v4_staging.txt` 残留在用户工程（并可能被 Unity 导入）。

- **最小修复方向**：`try/finally` 中无条件 `rm(join(PROJECT, staging), { force: true })`；同时把 staging 放到 `Library/` 或临时目录（不在 `Assets/` 下，避免触发导入）。
- **关联优化任务**：AA-OPT-008

### [P2] AA-CONSIST-001 — 统一陈旧阈值的来源与优先级

- **位置**：`packages/dsh-bridge/transport/mailbox.mjs` → `probeHeartbeat(projectPath,{staleMs})`；`core/bridge.mjs` 构造默认 `staleMs=15000`；`scripts/bridge-cli.mjs` 不传 `staleMs`
- **证据等级**：已验证（代码路径）
- **触发条件**：编辑器心跳间隔 > 6000ms（探针自述 `staleAfterMs`）但进程存活。
- **错误行为**：CLI 的 `inspect`/`discover` 用探针自述值（6000ms）→ 判 `idle`；DSH 插件用构造默认值（15000ms）→ 仍判 `ready`。**同一实例、同一时刻、两种结论**。
- **影响**：ASECLI 若以 CLI 判定为准，会在编辑器短暂卡顿时误判「需唤醒/不可用」；反之若以 DSH 为准，又拿不到自述值。文档声称「阈值优先取心跳自述」，但实现上 DSH 的显式参数覆盖了它，叙事与行为不一致。
- **最小修复方向**：明确优先级为「显式 `staleMs` > 心跳自述 > 15000 兜底」，并让 `Bridge` 默认**不传** `staleMs`（走自述），或把自述值作为下限参与计算；文档同步。
- **关联优化任务**：AA-OPT-009

### [P3] AA-PERF-002 — 用队列替代 `List.RemoveAt(0)` 管理句柄淘汰

- **位置**：`DSHBridgeProbe.cs.tpl` → `PutHandle(...)`（`_handleOrder` + `HandleLimit=4000`）
- **证据等级**：已验证（代码审查）
- **触发条件**：连续产生 > 4000 个句柄（如反复展开大数组）。
- **错误行为**：每次 `PutHandle` 在容量达上限时执行 `_handleOrder.RemoveAt(0)`，需移动约 4000 个元素；批量描述 500 个对象时约 200 万次元素移动。
- **影响**：毫秒级开销，与 AA-PERF-001 叠加会放大单次调用耗时，但非功能缺陷。
- **最小修复方向**：改用 `Queue<string>`（`Dequeue` 摊销 O(1)）。
- **关联优化任务**：AA-OPT-010

### [P3] AA-POLICY-001 — 允许把默认危险能力移出「需授权」集合

- **位置**：`packages/dsh-bridge/index.mjs` → `resolveConfig`（`extraDangerous`）；`safety/policy.mjs` → `authorizeCapability(capability,{dangerous})`
- **证据等级**：已验证（代码审查）
- **触发条件**：用户希望「某些默认危险能力在本项目里根本不允许」（例如组织策略禁止 `unity.asset.delete`）。
- **错误行为**：`dangerous` 列表只能通过 `[...DEFAULT_DANGEROUS, ...extraDangerous]` **追加**，无法移除。想禁止某项只能「不放进 allowDangerous」——但那是「需要显式授权」，用户仍可自行授权；无法表达「永久禁止」。
- **影响**：策略表达能力不足，与「最小权限」的组织诉求冲突；不是安全漏洞（默认仍关闭），但会迫使组织用文档而非配置来约束。
- **最小修复方向**：新增 `denied:[]`（探针侧硬拒绝，类似 `_blockedCapabilities`）并渲染进授权快照；或在 `resolveConfig` 支持 `dangerous` 的「覆盖」语义（传 `null` 项表示移除）。
- **关联优化任务**：AA-OPT-011

## 测试与观测缺口

**缺失用例**
- `resultTruncated=true` × 三种 `reason`（depth/items/nodes）——**核心能力的关键分支零覆盖**
- `code.execute` 的 `references`（正常/越界）、`backend:"roslyn"` 强制回退、`script_async_unsupported`
- `api.batch` 的 `stopOnError:false`（多失败）、`undoGroupOpened:false`（Undo 不可用）、补偿自身失败
- `DescribeEx` 的混合类型键、循环引用（`cycle` reason）
- `bridge-cli` 的 `install`/`call` 授权与审计行为
- CLI 与 DSH 的 `staleMs` 判定一致性

**缺失日志/指标/审计事件**
- CLI 路径的 `install`/`call` 审计（AA-OBS-001）
- `code.execute` 的慢调用告警（`elapsedMs` 超阈值时写事件，而不只是返回值里带）
- 引用集构建耗时（用于验证 AA-PERF-001 修复效果）
- 授权快照内容的变更审计（谁在何时授予了哪些能力）

## 残留风险

- **未覆盖区域**：`unity.code.execute` 的**恶意代码面**（本审计只评估了「挂死」与「无痕迹」两个可判定风险；不评估代码本身会做什么——这已被用户显式接受为「最大自由度」）。
- **未覆盖区域**：MCP 等价性对比只跑了单个 shader 的几何路径（V6 已逐字节一致），未覆盖建图（`create`）、重编译（`recompile`）、连线布局（`wire_route`）三条路径的等价性。
- **为何还不能安心发布**：`AA-DATA-001`（静默丢数据）与 `AA-OBS-001`（CLI 无审计/绕过授权）都会在**正常使用路径**上发生，不需要攻击者刻意构造；`AA-LIMIT-001` 是本次改造新增的「编辑器整体不可用」失败模式。

## 总评

- **结论**：**条件通过**
- **理由**：4 项能力 + `code.execute` 在真机 V1–V6 均通过，门禁（98 测试 / 探针编译 / 文档一致性 / openspec / project-architect）全绿，功能目标达成。但本次审计发现的 4 个 P1 中有 3 个位于**正常使用路径**（数据静默丢失、无审计、新失败模式），与项目既有治理基线（AA-OBS-002 审计覆盖、AA-OPT-002 路径边界）存在回退。
- **前置条件（发布前必须）**：
  1. `AA-OPT-001`：消除 `DescribeEx` 键冲突的静默丢弃（或显式标记）
  2. `AA-OPT-003`：CLI 接入审计，`install` 的授权来源受控
  3. `AA-OPT-002`：诊断列表有界
  4. `AA-OPT-004`：至少落地「慢调用可观测」+ 文档明示不可中断
- **可延后**：P2 其余项与 P3 全部，但 `AA-OPT-005`（引用集缓存）建议紧随其后，因为它与 `AA-LIMIT-001` 的主线程阻塞时间直接相关。
