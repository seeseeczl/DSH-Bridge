## 威胁与失败模型

- **资产**：开发者工程（`Assets/`、`ProjectSettings/`、场景与预制体）不可恢复的丢失；开发者本机任意文件（被诱导模型写入工程外）；DSH 自身的 Agent 提示词与知识库；"桥说成功了"这一判断的可信度。
- **最贵失败**：① 一次"看起来只是刷新一下"的调用把 `Assets/` 删除或把编辑器退出，且模型还收到 `ok:true`；② 模型在 `unity.asset.read` 里读到 `.env`/`id_rsa` 并把内容回显到对话与审计日志；③ 调用超时后模型重试一次，导致同一次破坏性操作被执行两遍。
- **本轮的核心结论**：v0.0.1 把**"是否危险"的判断放错了层**。内核只对 1 个能力名做白名单，而真正的执行面（反射调用、任意文件读写、菜单执行）在探针里**完全没有授权概念**——探针无条件信任 inbox 里的任何请求。

## Findings 详情

### [P0] AA-SEC-001 — 默认放行的 `unity.api.invoke` 等于"任意非公开静态方法"特权 — `safety/policy.mjs:7` + `probe/DSHBridgeProbe.cs.tpl:510,570`

- **证据等级**：已验证
- **触发条件**：默认配置（`DEFAULT_DANGEROUS = ['unity.reflect.invoke']`）下，模型被任何一段第三方文本诱导，发起
  `bridge_call(instance, "unity.api.invoke", { type: "UnityEditor.EditorApplication", member: "Exit", args: [0] })`
  或 `{ member: "ExecuteMenuItem", args: ["Assets/Reimport All"] }`。
- **错误行为**：`bridge.capabilities()` 只在危险清单里列出 `unity.reflect.invoke`；`unity.api.invoke`、`unity.api.members`、`unity.menu.execute`、`unity.asset.refresh` 全部**无需任何开关**。探针侧 `ApiInvoke` 用
  `BindingFlags.Public | BindingFlags.NonPublic | BindingFlags.FlattenHierarchy | BindingFlags.Static`
  遍历任意类型，`SetMember`/`ResolveMember` 同样带 `NonPublic`；`MenuExecute` 直通 `EditorApplication.ExecuteMenuItem`（含 `Assets/Reimport All`、`File/Exit`、`Window/General/Test Runner` 等任意菜单项）。`api.invoke` 还能 `prop.SetValue`/`field.SetValue` 写静态字段——包括 `EditorApplication.isPlaying`、脚本装配定义、甚至 `Application.*` 之外的静态状态。
- **动态复现**（`/tmp/dsh-bridge-audit2/minimal-audit.mjs`，`auditPath:null`，默认危险清单）：
  ```text
  危险清单只含: [ 'unity.reflect.invoke' ]
  unity.api.invoke {"type":"UnityEditor.EditorApplication","member":"Exit","args":[0]} -> {"accepted":"unity.api.invoke"}
  unity.api.invoke {"type":"UnityEditor.EditorApplication","member":"ExecuteMenuItem","args":["Assets/Reimport All"]} -> {"accepted":"unity.api.invoke"}
  unity.asset.delete {"path":"Assets"} -> {"accepted":"unity.asset.delete"}
  ```
  三条请求都**通过了授权检查并被投递到探针**。
- **影响**：`unity.reflect.invoke` 的白名单设计（SEC-0001 §40 "白名单 + 配置开关 + 默认拒绝"）实际保护的是一个**被 `api.invoke` 全覆盖的子集**。任何"反射是危险的就默认关掉"的安全承诺不成立。对一个会主动读取工程内容、网页、issue 的 Agent 来说，这是把"提示词注入 → 宿主进程任意成员调用"的路径打通了。
- **最小修复方向**：把 `unity.api.invoke` / `unity.api.members` / `unity.menu.execute` / `unity.asset.refresh`（含 ForceUpdate）/ `unity.importer.set` / `unity.asset.delete/move/rename/duplicate` 纳入危险清单；`api.invoke` 再收紧为"仅公开成员 + 类型/成员 deny-list + 只读模式"，并对 `EditorApplication.Exit` / `ExecuteMenuItem` / 装配定义 设硬拒绝。
- **关联优化任务**：AA-OPT-001

### [P0] AA-SEC-002 — `unity.asset.read` / `unity.search.content` 可读工程外任意文本文件并把内容回传对话 — `probe/DSHBridgeProbe.cs.tpl:642-658,602-640`

- **证据等级**：已验证（代码路径）/ 高置信推断（具体危害）
- **触发条件**：调用 `unity.asset.read({ path: "/Users/<u>/.ssh/id_rsa" })` 或
  `{ path: "/Users/<u>/.aws/credentials" }`；相对路径按**编辑器进程 cwd** 解析。`search.content({ query: "password", folders: ["/"], extensions: [".env"] })` 会走 `AssetDatabase.FindAssets` 再退化为 `ReadAllLines`。
- **错误行为**：`AssetRead` 只有 `if (string.IsNullOrEmpty(path))` 一句校验，随后
  `System.IO.File.ReadAllLines(path)` 直接读；`WriteTextAsset` 的对照实现（`Path.Combine(_projectRoot, path)`）说明作者本意是"相对工程根"，但 `AssetRead` **连 `_projectRoot` 都没用**。探针里不存在任何 `StartsWith(_projectRoot)` / `GetFullPath` 边界校验（全仓库 grep 结果为 0）。
- **影响**：能力名 `unity.asset.read` 与工具描述让模型相信"这是读 Unity 资产"。实际效果是**目标工程进程权限内的任意文本读取**，内容经 `bridge_call` 的 `data` 全量回显到会话、并（`summarize` 200 字符）写入 `~/.dsh/bridge/audit.log`。典型被利用方式是"帮我看看这个工程为什么构建失败" → 模型顺手读 `.env`/`credentials`/浏览器保存的密钥文件。这与 SEC-0001 的"最小权限"承诺直接冲突。
- **最小修复方向**：路径先 `Path.GetFullPath` 再要求以 `_projectRoot` 为前缀；`search.content` 限定在 `AssetDatabase` 内的资产路径（`GUIDToAssetPath` 结果本来就在工程内，但 `folders` 参数未校验）；顺手给 `asset.read` 加"仅资产扩展名"过滤。
- **关联优化任务**：AA-OPT-002

### [P0] AA-SEC-003 — `unity.asset.create` 的 `path` 直接拼接工程根，`../` 可写到工程外任意位置 — `probe/DSHBridgeProbe.cs.tpl:660-721`

- **证据等级**：已验证
- **触发条件**：`unity.asset.create({ kind: "script", path: "../../../../Users/<u>/Library/LaunchAgents/com.x.plist", content: "..." })` 或任意 `kind: "text"`。
- **错误行为**：
  ```csharp
  static void WriteTextAsset(string path, string content) {
      var full = System.IO.Path.Combine(_projectRoot, path);   // 717
      ...
      System.IO.File.WriteAllText(full, content, ...);          // 720
  ```
  `Path.Combine` 遇到 `..` 不拒绝、遇到绝对路径会**直接丢弃** `_projectRoot`；`Directory.CreateDirectory(dir)` 会自动创建整条路径。`unity.importer.set` 的 `changes` 走 `SetValue` 反射，也可写越界值。
- **影响**：从"写工程"升级为"写本机任意文件"——写 `~/Library/LaunchAgents/*.plist` + 下一个 `launchctl` 触发即持久化；写 `~/.zshrc`、写 `~/.dsh/skills/**/SKILL.md`（直接影响后续 Agent 行为）、写 `~/.codex/config.toml`。这条路径**完全不需要反射**，`kind:"text"` + `content` 就够了，也不需要任何危险开关。
- **最小修复方向**：同 AA-SEC-002，统一走一个 `ResolveProjectPath()`（`GetFullPath` + 前缀校验 + 拒绝绝对路径）；`asset.create` 仅允许 `.cs/.shader/.txt/.json/.mat/.asset/.prefab` 等资产扩展名，或改用 `AssetDatabase` API 而非 `File.WriteAllText`。
- **关联优化任务**：AA-OPT-003

### [P1] AA-CONC-001 — 探针在执行**之前**就删掉了 inbox 原始请求，执行期超时后内核无法撤回 — `probe/DSHBridgeProbe.cs.tpl:172-179`

- **证据等级**：已验证
- **触发条件**：任一合法调用在**探针侧执行耗时**超过 DSH 侧 `timeoutMs`（默认 30s，Agent 常用 3–10s）。真实触发源：`AssetDatabase.Refresh(ForceUpdate)`、大工程导入、`search.content` 扫全库、域重载前的最后一次 `Refresh`。
- **错误行为**：探针 `HandleFile` 第一件事就是
  ```csharp
  File.Move(path, donePath);   // 172-179：先搬走，再解析、再判过期、再执行
  ```
  因此 `issuedAt + deadlineMs` 的过期校验（213 行）只覆盖"**排队**中已过期"，**不覆盖"执行中已超时"**。DSH 侧 `purgeRequest()` 找不到文件（已 move 走）而静默失败——但请求**已经在执行**，无法回滚。
  动态复现（`onCall` 延迟 600ms，`timeoutMs: 300`）：
  ```text
  DSH 返回: {"code":"timeout"} | 探针实际执行次数: 1 | done/ 文件数: 1
  ```
- **影响**：`AA-CONC-002`（上一轮的"超时后延迟执行"）只修好了一半。剩余的一半更糟：模型看到 `timeout` → 按工具描述"可能未运行/重载/探针不匹配"重试 → **同一次破坏性操作执行两次**。对 `asset.delete`、`gameobject.delete`、`prefab.save` 这类非幂等操作，这是数据损坏路径。上一轮报告的 P0 修复结论"超时后不存在延迟副作用"因此**不成立**。
- **最小修复方向**：① 执行前先写 `in-progress/<id>.json` 保留原请求，执行完再移入 `done/`；② DSH 侧超时后检查 `in-progress`，若仍在执行则返回 `in_flight` 而不是裸 `timeout`，并在工具渲染里明确"请求可能已生效，不要重试"；③ 为长时间能力加 `progress` 事件。
- **关联优化任务**：AA-OPT-004

### [P1] AA-CONC-002 — 同工程双编辑器下发现结果与实际执行者不一致且不可观测 — `probe/DSHBridgeProbe.cs.tpl:102-127` + `core/bridge.mjs:56-85`

- **证据等级**：已验证
- **触发条件**：① Unity 域重载空窗（旧进程已退出、新进程已启动）；② 用户复制工程后在两处打开（`Application.dataPath` 相同 → `sha1` 相同 → `instanceId` 相同）；③ 某些版本允许双开。
- **错误行为**：`LoadOrCreateIdentity` 只要 `pid + startTicks` 匹配就**复用旧 `bootId`**；两个不同进程的 `Application.dataPath` 相同 → `_instanceId` 相同。双方都认为自己拥有 `<root>/<bootId>/inbox`，谁先 `GetFiles` 谁执行。而 `bridge.targets()` 的 `duplicates` 分支只是在**同一批候选**里做标记——当候选只有 1 个（正常情况）而 `instance.json` 被另一个进程覆盖时，桥会读到 B 的 `bootId` 并把请求写进 B 的通道，同时把发现结果里的 `pid` 保留为 A。
  动态复现：
  ```text
  发现结果数: 1 | detect 报的 pid: 84230 | 实例缓存 pid: 84230 | 实际执行者: B
  A 收到请求: 0 次, B 收到请求: 1 次
  ```
- **影响**：Agent 认为自己在操作"实例 A（pid 84230，用户刚打开的那个）"，实际指令进了**另一个编辑器进程**——可能正在 Play Mode、可能开着不同的场景、可能是用户复制出来做实验的工程副本。审计日志记录的 `instanceId` 也区分不出。这类错误在用户侧表现为"我让它改 A 工程，B 工程变了"。
- **最小修复方向**：`instanceId` 稳定段加入进程启动指纹（或至少让 `duplicates` 基于 `instance.json` 的实际 `pid` 判定）；探针在复用 `bootId` 前必须校验 `pid` 与 `startTicks` 均一致（目前已有，但 A 已退出时 B 会看到 `pid` 不同而**新建** `bootId` —— 需确认 B 新建后 A 的旧目录不再被使用）；`bridge_targets` 暴露 `duplicates[].pid` 与 channel 所有者。
- **关联优化任务**：AA-OPT-005

### [P1] AA-CODE-001 — `ResolveTarget` 返回 `(null, null)` 时 `staticType ?? target.GetType()` 必抛 NRE — `probe/DSHBridgeProbe.cs.tpl:520,574`

- **证据等级**：已验证（同形态 C# 代码在 `mono 6.12` 上复现）
- **触发条件**：`unity.api.invoke` / `unity.api.members` 在**未给** `handle/path/asset/type` 且 `Selection.activeObject == null` 时。
- **错误行为**：`ResolveTarget` 的末尾
  ```csharp
  if (Selection.activeObject != null) return Selection.activeObject;
  throw new KnownError("invalid_argument", "需要 handle / path / asset / type 之一");  // 484-485
  ```
  看起来会 throw——**但 `Selection.activeObject` 是 `UnityEngine.Object` 的隐式布尔重载**，Unity 销毁后对象是 `!= null` 但 `Equals(null)` 为真的"假空对象"；更关键的是 `ApiMembers` 的第一行直接
  ```csharp
  var type = staticType ?? target.GetType();   // 574：target 只会来自非 type 分支，若为假空对象则 NRE
  ```
  且 `ApiInvoke` 在 `kind` 为 `property/field` 且目标为 `type` 时 `target` 为 `null` 而 `staticType` 非空，此路安全；反之 `staticType` 为 `null`、`target` 为假空对象时 `target.GetType()` 必然 NRE（同形态复现：`THROW NullReferenceException`）。
- **影响**：这是一条**维护路径必炸**的代码：任何'先探测成员再调用'的 Agent 工作流（模型先 `api.members` 看签名、再 `api.invoke`）在编辑器刚重新加载、选择为空时会得到 `probe_error`/`NullReferenceException`，而不是可理解的 `invalid_argument`。模型倾向于把它解释成"桥坏了"。
- **最小修复方向**：`ResolveTarget` 末尾改为 `throw`（去掉隐式 bool 判断）并显式 `if (target == null) throw`；`ApiInvoke/ApiMembers` 加 `if (target == null && staticType == null) throw new KnownError(...)`。
- **关联优化任务**：AA-OPT-006

### [P1] AA-COVER-001 — "回归 16 条全绿"是假覆盖：探针只有病毒式断言，执行面零测试 — `tests/unit/events-contract.test.mjs`、`tests/unity-probe/compile-check.mjs`

- **证据等级**：已验证
- **触发条件**：任何人相信 `npm run verify` 全绿 = 第 4 节列出的 P0 不存在。
- **错误行为**：

### [P2] AA-DATA-001 — 同一工程的重启只换 `bootId`，旧通道目录永不回收 — `probe/DSHBridgeProbe.cs.tpl:81-88`、`transport/maintenance.mjs`

### [P3] AA-EVENT-002 — 失败日志风暴下按序清理会丢最新事件 — `transport/maintenance.mjs:19-45`

- **证据等级**：高置信推断
- **触发条件**：工程每帧报错（Shader 编译错误循环、MissingReference 风暴），事件以 >10 条/秒产生，而 `sweepEvents` 的 `keep=500` 窗口在 `bridge_events` 调用之间被打满。
- **错误行为**：`sweepEvents` 按 `seq` 排序后保留最后 `keep` 条——但当产生速率高于读取速率时，**读取窗口里的越界事件在被读到之前就被删掉**：`readEvents` 先 `listJson` 再逐条读，`sweepEvents` 紧随其后执行；两个 DSH 会话共享同一 events 目录时，先 `sweep` 的那个会删掉另一个还没读到的条目。

### [P3] AA-CODE-002 — `_typeCache` 缓存 `null`；`FindType` 全量 `GetTypes()` 每个未命中名扫一遍全程序集

- **证据等级**：已验证（语义）/ 高置信推断（影响）

## 测试与观测缺口

- **缺失用例**：
  - 能力语义：41 个能力**零覆盖**。最小集合应是 `asset.read`/`asset.create` 越界拒绝、`api.invoke` 危险名单、`api.members` 空选择不 NRE、`asset.delete` 路径边界。
  - 执行期超时：`AA-CONC-001` 没有用例（`timeout.test.mjs` 只覆盖"探针完全不收"）。
  - 同工程双编辑器：`concurrency.test.mjs` 只测同一 editor 的并发，不测两个 editor 抢同一 bootId 目录。
  - 探针 `GetStringList`/`CoerceValue` 对类型不匹配参数的行为。
- **缺失观测**：
  - 探针侧无"请求被拒"事件（`path_escape`、`capability_denied` 都只返回错误、不写事件），因此**一次被注入的越权尝试在事件流里完全不可见**。
  - 审计日志不含 `bridge_uninstall`/`bridge_preinstall`/`bridge_knowledge_*`。
  - 无 `inFlight` / 中心执行时长指标，AA-CONC-001 的事故无法事后定位。
  - `anchor` 里 `done/*.json` 的请求正文与 `inbox` 的请求正文都含参数原文，无轮转。

## 残留风险

- **真实 Unity 未验证**：本报告所有探针侧结论均基于源码 + 同形态 C# 复现 + stub 语义。`EditorUtility.scriptCompilationFailed` 的可见性、`Selection.activeObject` 的假空行为、`AssetDatabase.FindAssets("")` 在大工程的实际耗时，仍需实机确认（上一轮 R5 仍未关闭）。
- **`sweepEvents` 跨会话语义**：read-then-sweep 的顺序在单会话下安全，多会话共享 events 目录时存在丢失窗口（AA-EVENT-002，高置信推断）。
- **知识库路径**：本轮顺带核查了 `core/knowledge.mjs`，`slugify` 把 `/` 替换为 `-`，`readTopic`/`removeTopic` 用原始输入拼路径——`removeTopic('../x')` 可删同级文件（实测返回 `true` 并删除了兄弟目录下的 `IMPORTANT.md`）。该缺陷要求模型调用 `bridge_knowledge_delete` 传入 `../`，触发条件苛刻、影响限于 `~/.dsh/bridge/knowledge/`，故**未单列 finding**，但已并入 AA-OPT-016 一并修。
- **为何还不能安心发布**：本轮的 P0 全部集中在"探针无条件信任请求"这一条根因上。修不修它们，决定了 DSH-Bridge 是"一个会替你在工程里动手的助手"还是"一个能从任意第三方文本被遥控的本机执行器"。

## 总评

- **结论：阻塞**。
- **理由**：v0.0.1 的**协议层**（四元组配对、原子投递、精确取件、零端口、多实例隔离）设计是扎实的，上一轮 P0 也确已修复。但本轮把攻击面从"传输"推进到"执行"后发现：**授权模型与执行面严重不匹配**——内核只认 1 个能力名，探针里另有 4 条等价特权路径（任意静态反射、任意文件读、任意文件写、任意菜单执行）全部默认开启，且**没有一条测试能失败**。一个能读取工程/网页/issue 的 Agent，与一个"读到什么就照做什么"的本机特权执行器对接，是典型的提示词注入到 RCE 的升格路径。再加上执行期超时不可撤回（会让模型重复执行破坏性操作），当前版本不适合对外发布，也不宜在"真实生产工程"里长期开着。
- **前置条件**：
